# 需求梳理版 · 用户管理

> 源需求：[需求-用户管理.md](../requirements/需求-用户管理.md)  
> 状态：可评审 / 可排期  
> 结论摘要：Admin 提供用户管理完整 CRUD 页；Nest 新增仅 `admin` 角色可调用的管理端用户接口。权限菜单仍 stub 全通，接口层强制校验角色。物理删除、会员 `plan`、细粒度 RBAC 本期不做。

---

## 1. 产品定位

| 项 | 说明 |
|----|------|
| 产品 | 织序后台（`admin/`）的用户管理 |
| 使用者 | 持有 Nest `User.role = admin` 的运营/管理员 |
| 管理对象 | Nest `User` 全量账号（含 `user` 与 `admin`） |
| 协作项目 | **Admin** 页面 / API 封装；**NestJS** 管理端接口与角色守卫（现有模型不改表也可落地） |
| 不做什么 | 不做菜单/按钮 RBAC；不恢复 O2O `bo/user`；不物理删用户；不做会员配额/`plan` 业务 |
| 成功标准 | 管理员可在后台完成：查、建、改资料、改角色、启停、重置密码；非 admin 调接口被拒绝 |

## 2. 用户与用例

| ID | 角色 | 用例 | 优先级 | 验收要点 |
|----|------|------|--------|----------|
| UC-01 | 管理员 | 打开「用户管理」列表，分页查看用户 | Must | 展示 id、邮箱、用户名、角色、状态、创建时间；分页可用 |
| UC-02 | 管理员 | 按关键字（邮箱/用户名）、状态、角色筛选 | Must | 条件组合查询正确；重置筛选恢复全量分页 |
| UC-03 | 管理员 | 新建用户（邮箱 + 密码，可选用户名/角色） | Must | 创建成功后出现在列表；默认角色 `user`、默认状态 `active`（无需邮箱验证码） |
| UC-04 | 管理员 | 编辑资料（用户名、角色；邮箱见 Q-05） | Must | 用户名唯一冲突有明确提示；保存后列表刷新 |
| UC-05 | 管理员 | 启用 / 禁用账号 | Must | `disabled` 后该账号无法登录 Nest；可再启用为 `active` |
| UC-06 | 管理员 | 将待验证账号直接激活 | Must | `pending_verification` → `active` 无需验证码 |
| UC-07 | 管理员 | 重置密码 | Must | 管理员设定新密码（长度规则同注册）；旧 refresh 会话作废 |
| UC-08 | 管理员 | 改角色 `user` ↔ `admin` | Must | 生效后该账号下次鉴权带新角色 |
| UC-09 | 系统 | 保护最后一个 admin / 禁止自残 | Must | 不能禁用、降级「最后一个 admin」；不能禁用/降级当前登录自己（Q-03） |
| UC-10 | 非 admin | 调用管理端用户接口 | Must | 401/403，无列表数据泄露 |
| UC-11 | 管理员 | 表单校验与错误提示（邮箱占用、用户名占用、密码过短） | Must | 与 Nest 错误码可对应到界面文案 |
| UC-12 | 管理员 | 侧栏进入用户管理页（静态路由） | Must | `elegant-router` 两层约定；`zh-cn` 路由/页面文案齐全 |
| UC-13 | 开发者 | 本地可用 Nest 管理员账号联调 | Should | 文档或种子说明如何得到一个 `admin` 账号 |
| UC-14 | 管理员 | 修改登录邮箱 | Should | 唯一性校验；改后用新邮箱登录 |
| UC-15 | 模板开发 | `VITE_AUTH_MOCK=Y` 时页面仍可点（mock 列表） | Could | 不阻塞无后端时的 UI 开发；正式验收走真实 Nest |
| UC-16 | 管理员 | 导出用户列表 | Won't | 本期不做 |

## 3. 功能拆解

### 3.1 Admin（后台前端）

| 模块 | 范围 | 备注 |
|------|------|------|
| 页面 | `views/` 下最多两层路由的用户列表页 | `JQCustomPage` + `JQSearch` + `JQDataTable` + `JQDialogForm`；无需 PageMenu Tab（单列表即可） |
| API | `service/api` 用户管理模块 + `typings/api` | 禁止页面直连 axios；url 不含网关前缀 |
| 登录衔接 | 管理接口需携带 Nest JWT | 见 Q-01：本期默认把后台登录接到 Nest 邮箱密码（仅 `active`）；mock 仅作 UI 旁路 |
| i18n | `route.*` + `page.*`，至少 `zh-cn` | 可复用/改写已有 `page.manage.user` 骨架，去掉性别/手机等无字段项 |
| 权限 UI | 不新增 `PRIV` / `roleConfig` / `v-auth` 业务树 | 菜单对已登录者可见（stub）；真正拦在接口 |

### 3.2 NestJS（服务器）

| 模块 | 范围 | 备注 |
|------|------|------|
| 管理端 API | 列表分页、创建、更新资料、改状态、改角色、重置密码 | 独立于现有 `/auth/register|login`；建议前缀如 `/admin/users`（技术设计定稿） |
| 鉴权 | JWT + **`role === admin` 守卫**（现状无 RolesGuard，需新增） | 非 admin 一律拒绝 |
| 数据 | 沿用 Prisma `User` | 不返回 `passwordHash`；不改枚举语义 |
| 创建策略 | 后台创建直接 `active` | 不走邮箱验证码流（Q-02） |
| 重置密码 | bcrypt 写新 hash，撤销该用户未过期 refresh token | 与现网 `logout` 语义对齐 |
| 安全 | 最后 admin 保护；禁止操作自身禁用/降级 | UC-09 |

### 3.3 现有能力对照（不重复造轮子）

| 已有 | 本需求用法 |
|------|------------|
| `User` / `UserStatus` / `UserRole` | 管理对象，不扩枚举 |
| `POST /auth/register` 等 | **终端用户自助注册**，后台创建不复用该接口（避免验证码与默认 `user` 角色限制） |
| Admin 登录 mock、`/bo/user` 旧路径 | 本期管理功能不以旧 O2O 接口为准 |
| privilege stub | 保持；不在本需求做菜单裁剪 |

## 4. 非功能需求

| ID | 类型 | 要求 |
|----|------|------|
| NFR-01 | 安全 | 管理接口必须 admin；密码不明文回传；重置后旧会话失效 |
| NFR-02 | 一致 | 邮箱小写存储（与现 `auth` 一致）；用户名/邮箱唯一 |
| NFR-03 | 协议 | Admin 请求层当前认 `{ code, data }`，Nest 现为 HTTP + 裸 JSON；本需求必须可联调（适配方案见技术设计 / Q-07） |
| NFR-04 | 可维护 | API 只从 `@/service/api` 引入；Nest 契约以 Swagger `/docs` 为准 |
| NFR-05 | 可观测 | 管理写操作记安全日志（创建/禁用/改角色/重置密码），不含密码 |
| NFR-06 | i18n | 默认 `zh-cn`；生产代码无 `console.log` |
| NFR-07 | 文档归属 | 产品流水线文档放 `admin/docs`；Nest 实现细节在技术设计写清，不另起一份平行需求源 |

## 5. 端到端流程（目标态）

```text
管理员用 Nest 邮箱密码登录 Admin（active + 持有 JWT）
  → 打开「用户管理」
  → 筛选 / 分页浏览
  → 新建用户（立即 active）或编辑资料 / 改角色
  → 禁用后该账号无法再登录；启用或激活待验证账号后可登录
  → 重置密码后旧 refresh 失效，用户用新密码登录
非 admin 持有普通用户 JWT 调用 /admin/users* → 拒绝
```

## 6. 范围 In / Out

| In（本需求） | Out（明确不做） |
|--------------|-----------------|
| Admin 用户列表 CRUD 页（查/建/改/启停/重置密码/改角色） | 物理删除用户 |
| Nest 管理端用户 API + admin 角色守卫 | 菜单/按钮 RBAC、角色管理、权限树 |
| 最后 admin 与「不能禁自己」保护 | 会员 `plan` 编辑与配额 |
| 后台创建即激活 | 自助注册/验邮改造（保持现有 `/auth/*`） |
| 重置密码并作废 refresh | 导出、批量导入、操作审计页 |
| 登录接到 Nest 以便拿到真实 JWT（Q-01 默认） | 桌面端 Electron 用户管理 |
| | 性别/手机号等模型中不存在的字段 |

## 8. 待澄清

| ID | 问题 | 默认（若未答复） | 影响 |
|----|------|------------------|------|
| Q-01 | 后台登录是否本期切到 Nest 邮箱密码？ | **切到 Nest**；`VITE_AUTH_MOCK=Y` 仅 UI 旁路，验收用真实登录 | 无 JWT 则管理接口无法测 |
| Q-02 | 后台创建是否跳过邮箱验证？ | **跳过**，直接 `active` | UC-03 |
| Q-03 | 能否禁用/降级当前登录账号？最后一个 admin？ | **都不能** | UC-09 |
| Q-04 | 是否提供物理删除？ | **否**，仅禁用 | 接口清单 |
| Q-05 | 是否允许改邮箱？ | **Should**：允许，需唯一 | UC-14 |
| Q-06 | 重置密码方式？ | **管理员直接设新密码** + 撤销 refresh | UC-07 |
| Q-07 | Admin `{code,data}` 与 Nest 裸 JSON 如何对齐？ | 技术设计定：优先 **Admin 用户模块适配 Nest HTTP**，避免全局改 `request/shared.ts`（规则禁止未批准改该文件） | NFR-03 |
| Q-08 | 非 admin 登录后能否看见菜单？ | **能看见**（stub）；接口拒绝。RBAC 另开需求 | UC-10 / 权限原则 |
| Q-09 | 待验证用户管理员能否直接激活？ | **能** | UC-06 |
| Q-10 | 创建时角色默认值？ | **`user`**，表单可选 `admin` | UC-03/08 |

未答复则按上表默认进入技术设计。

## 9. 验收标准

| ID | 标准 | 对应 |
|----|------|------|
| AC-01 | 管理员可分页、筛选查看用户列表，不含密码哈希 | UC-01/02 |
| AC-02 | 可创建用户：邮箱+密码必填；创建后为 `active`，可用该密码登录 Nest | UC-03 |
| AC-03 | 可改用户名、角色；用户名冲突返回可读错误 | UC-04/08/11 |

| AC-07 | 不能禁用/降级自己；不能去掉最后一个 admin | UC-09 |
| AC-08 | 非 admin JWT 访问管理接口失败 | UC-10 |
| AC-09 | 侧栏可进用户管理；`zh-cn` 文案完整；列表用 JQ* 约定组件 | UC-12 |
| AC-10 | 无新增 privilege 配置树；`v-auth` 仍 stub | Q-08 |

## 10. 风险摘要（梳理级）

| 风险 | 等级 | 对策方向 |
|------|------|----------|
| Admin 请求封装与 Nest 响应形态不一致 | 高 | Q-07：模块级适配，不擅自改全局 `shared.ts` |
| 无 admin 守卫导致普通用户可管全站账号 | 高 | 接口强制 `role=admin`，不依赖前端隐藏 |
| 菜单 stub 造成「看起来有权限」 | 中 | 文档写明；验收以接口为准 |
| 后台登录仍 mock，联调无 JWT | 高 | Q-01 默认切 Nest 登录 |
| 误禁唯一 admin 导致无法再进后台 | 高 | UC-09 服务端硬约束 |
| 后台创建与自助注册规则分叉 | 低 | 文档区分两条入口，不混用 `/auth/register` |
